# Git 协作与提交规范

本文约定深知 Harness 的提交信息和入库范围，便于审查和回溯。

---

## 一、入库范围

根目录 `.gitignore` 是白名单：默认忽略，只有显式放行的路径才会进入仓库。

可以入库的是源码、锁文件、方案定义、公开契约样例和文档。

不要入库：

- `.env`、模型密钥、私钥和连接串
- `var/` 中的任务、Run、对话和 DSH 会话
- 授权 PDF、实验归档、模型权重和数据集
- `node_modules/`、`dist/`、`dist-electron/`、截图和安装包

新增顶层文件或 `docs/` 子目录时，同步更新 `.gitignore` 的放行规则，否则文件会留在工作区却无法提交。

---

## 二、Commit 信息格式

```text
<type>: <中文描述>
```

- `type` 使用英文
- 描述使用中文，说明这次提交的目的

例如：

```text
feat: 为文本自检方案补充成果下载
fix: 修复 Run 取消后状态未落盘
docs: 整理 Harness 文档目录
```

---

## 三、常用类型

```text
feat      新增功能
fix       修复问题
refactor  重构，不改变主要行为
docs      文档
chore     配置、依赖、构建
test      测试
```

其他类型确有需要再用，不随意增加。

---

## 四、Commit 粒度

一个 Commit 对应一个明确目的。

推荐：

```text
docs: 整理 Harness 文档目录
```

避免把互不相关的修改放进同一个 Commit，也避免使用 `update`、`fix`、`修改代码` 这类无法判断内容的说明。

提交说明应能回答：改了什么，为什么改，出问题时该回看哪一次。

---

## 五、分支

功能开发使用短英文分支名，例如 `feat/run-events`、`fix/cancel-persist`、`docs/readme`。

不要把密钥或本机绝对路径写进分支说明、提交信息或文档。远程仓库的可见性由仓库管理员确认后再推送。
